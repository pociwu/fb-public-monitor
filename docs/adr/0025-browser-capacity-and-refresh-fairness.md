# 瀏覽器雙層每日額度與個資巡檢公平性

2026-09-08 使用者確認採用全域每日 32 批、單帳號每日 8 批。

問題證據：15 個帳號共用 8 批時，SerpApi 額度耗盡且 Bright Data 無結果，個資備援、匿名驗證與照片工作迅速耗盡每日額度。持久化補跑增加 pending 數量，但沒有增加來源容量。ADR 0005 的單帳號額度沒有被原實作獨立執行。

## 決策

- `browser_guard.global_daily_batches` 預設 32，`profile_daily_batches` 預設 8。舊 `daily_batches` 作為全域設定的相容別名，新鍵優先，不覆寫使用者明示的舊上限。
- `BrowserGuard.acquire` 在同一 SQLite 寫入交易中檢查、保留全域及單帳號計數；登入及匿名共用。超限不增加任何計數。台北午夜換日，重啟不清零，保留現有間隔、單工及熔斷。
- 個資備援等待／執行期間，普通巡檢跳過相同個資來源查詢，但不停止獨立的公開驗證與內容排程。
- 普通個資工作按今日瀏覽器服務批次、最近成功時間排序，避免同一個永遠失敗的舊帳號搶完額度。負優先序及 ADR 0009 的 4:1 公平性保留。
- 儀表板及工作篩選共用佇列分類：running、ready、limited、scheduled。ready 只代表到期，真正執行仍受 guard、來源、預算及維護狀態影響。

## 遷移與驗證

沿用 browser_limits 既有全域／profile 欄位，無 schema 變更，不刪除工作、媒體、游標或歷史，不改寫成功時間。舊 profile 計數原本未記錄，從第一次新版保留開始累計，全域舊計數保留。舊的次日補跑不提前。

`tests/test_refresh_capacity.py` 覆蓋設定相容、雙層限制／重啟／午夜、跨帳號公平性、備援抑制重查及儀表板計數／篩選；既有 BrowserGuard 測試驗證間隔、並行保留與熔斷仍有效。
